# Step 1.5: Bool and bit-vector values in models, and traces

Plan step 1.5, started 2026-11-10 on `bitwuzla-support` after `1ab43e7b`.
It is the first step done under the verification rules in `URA/CLAUDE.md`.

Goal: a `sat` answer from `smt-bw` comes with a model, so `--log=cex`
prints a counterexample trace and `--cex=FILE` writes a harness.

## What the code has to fit (read before writing it)

[FACT] Mono BMC asks for a model only to print a trace (`--log=cex`) or
write a harness (`--cex`): `BmcPass.cc:490-516`, `SolverBmc.cc:129-133`.
The trace calls `eval` with `complete = false` on Bool literals of the
formula (`BmcImpl.hh:6-46`) and on the symbolic value of each instruction
(`BmcImpl.hh:135,174`).

[FACT] When Z3 cannot evaluate a term, the Z3 model returns `nondet`
(`Z3.hh:397-423`). A null Expr would crash the trace code, which calls
`isOpX` on the result and `isOp` dereferences it (`ExprApi.hh:15-17`).

[OBS 2026-11-10] Bitwuzla 0.9.1 `get_value` (probe in the session
scratchpad, `probe15.cpp`):
- a constant in no assertion, made before or after the check, gets 0, the
  same each time, and terms over it agree (`y + z` = 0);
- after a later `assert_formula`, after `unsat`, before any check, or
  without `PRODUCE_MODELS`, it throws;
- after a second `sat` check it answers from the new model. So a model
  object kept from the first check would silently give values of another
  model. The adapter has to refuse that itself;
- on a bound variable it returns the variable, not a value, and
  `value<std::string>()` on that throws;
- `value<std::string>(10)` of a bit-vector is unsigned: 2^128-1 for a
  128-bit all-ones.

[OBS 2026-11-10] Z3's model prints the same bits in two ways: `inc.c`'s
`x` as `-1:bv(32)`, `branch.c`'s `%_3` as `0xfffffff9:bv(32)`. Z3 itself
returns `#xffffffff` (a C probe), so the sign comes from SeaHorn's glue.
The harness turns either into the same bits (`toAPInt`, `ExprLlvm.hh:198`).

[OBS 2026-11-10] With `smt-z3`, all four `sat` examples print a trace,
write a harness with `--cex`, and the harness reaches the error when run
(`sea cex --run`, "__VERIFIER_error was executed"). `test/cex` passes 5/5
with `smt-z3`. With `smt-bw` before this step, `--log=cex` exits:
"get_model is not supported yet".

[OBS 2026-11-10] `branch.c`, `divshift.c` and `overflow.c` have more than
one path to the error, so two correct models can give different traces.
Only `inc.c` has a single path.

[OBS 2026-11-10] The `test/cex` tests write their harness to a fixed file
in `/tmp`. If `smt-bw` wrote none, the second RUN line would run the
harness left by an earlier `smt-z3` run, and the test could pass falsely.

## Design decided before the code

- `get_model()` returns a model tied to the solver's generation: a counter
  that `add`, `check` and `reset` increase. A model used after any of
  them, or after the solver is gone, logs an error and answers `nondet`.
  `get_model()` when the last check was not `sat` gives a model that
  answers only `nondet`.
- `eval` encodes the term, asks Bitwuzla, and decodes Bool to true/false
  and a bit-vector to the unsigned numeral in [0, 2^w). Anything else
  (arrays, structs, a term the encoder rejects) gives `nondet`.
- Bitwuzla always completes a model, so `complete` true and false give the
  same values. That is still one satisfying assignment: a constant in no
  assertion cannot make an assertion false.
- **Differences from the plan text:** `nondet` rather than a null Expr
  (the plan's wording), because callers crash on null and already handle
  `nondet` from Z3. "The same blocks as `smt-z3`" is required only for
  `inc.c`; for the other examples, running the counterexample is the
  check (see above).

## Pass criteria (written before the code)

Models, unit tests in `units_bitwuzla`:
- M1. Values: after `x + 1 = 0` on 8 bits is `sat`, `eval(x)` is the 8-bit
  numeral 255. Bool constants give true or false. Widths 1 and 128 decode
  exactly (128-bit all-ones is 2^128-1).
- M2. Stale models are refused. After a later `add`, a later check, a
  `reset`, or the solver's destruction, `eval` gives `nondet`, never a
  value. `get_model()` after `unsat`, after `unknown`, or before any check
  gives a model that answers `nondet`.
- M3. A term the encoder rejects (an integer, an array) gives `nondet`, and
  the solver still answers correctly afterwards.
- M4. `complete` true and false give the same value. A constant in no
  assertion gets a value, consistent with terms over it.

Differential testing against Z3, in the random-formula fuzzer:
- D1. For every `sat` formula, the values of its constants come through
  `get_model()->eval`, and Z3 accepts them: 0 rejected models.
- D2. Every subterm of every `sat` formula, and a term over a constant
  that is in no assertion, is evaluated through the model. Z3, given the
  same constant values, gets the same value: 0 mismatches, 0 non-values.
- D3. The fuzzer's earlier checks still pass (0 disagreements, every
  formula `SAME` in the formula check).

End to end:
- E1. `inc.c` with `--log=cex`: `smt-bw` prints a trace with the same
  blocks as `smt-z3`, and `x` is 4294967295 (0xffffffff).
- E2. For each `sat` example (`inc`, `branch`, `divshift`, `overflow`),
  with both solvers: the trace is printed, `--cex` writes a harness, and
  `sea cex --run` on it prints "__VERIFIER_error was executed". The values
  the trace shows for the nondet calls equal the harness's values. A
  harness with a value changed on purpose must not reach the error, so the
  check can fail.
- E3. `test/cex` with `smt-bw`, with the `/tmp` harness files deleted
  before each test: every test whose formula `smt-bw` can encode passes;
  each of the others answers `unknown` and is named with its operator.
- E4. No regression: opsem/opsem2 answers as before (106 same as `smt-z3`,
  69 `unknown`, 1 no answer from either, 0 different); formula check 0
  `DIFFERENT`; examples, selector and detection pass; `verify_all` passes.

Rules from `URA/CLAUDE.md`:
- U1. Mutation: a separate agent, which has not seen the tests, writes bugs
  for the new code. Each is caught, or explained (equivalent, or safe).
- C1. Coverage: every new line is run by a test or listed with a reason.
- R1. A fresh review of the code against the spec, each finding checked.
- S1. Every way `eval` can fail gives `nondet`; the correctness case says
  why no caller can take it for a value.

## What was built

[FACT] SeaHorn commit `8b85c705` (branch bitwuzla-support), "feat(smt):
models for the Bitwuzla adapter":
- `BitwuzlaModelImpl.hh/.cc` (new): the model. It holds a `weak_ptr` to
  the solver and the generation it was made in, and asks the solver for
  each value.
- `BitwuzlaSolverImpl`:
  - a generation counter that `add`, `check` and `reset` increase (it
    starts at 1, so 0 is never current), and the generation of the last
    `sat` check;
  - `get_model()` gives a model of the current generation only if the last
    check was `sat` with no change since; otherwise it logs an error and
    gives a model of generation 0, which never has values;
  - `eval_in_model`: refuses an old generation, then encodes, calls
    `get_value`, decodes; `nondet` for anything else;
  - `print_model`: `name = value` for the constants of the assertions since
    the last `reset`, sorted by name, found without recursion.
- `decode_bitwuzla_value` in `MarshalBitwuzla.cc`: Bool to true/false,
  bit-vector to the unsigned numeral (`value<std::string>(10)`), null for
  anything else.
- Tests in `units_bitwuzla`: 6 new test cases (model values; model after a
  change; after an assertion it cannot encode; terms it cannot evaluate;
  decoding; printing). The fuzzer now takes every value through
  `get_model()->eval` and compares every subterm with Z3.

Scripts (URA/scratch, not in git):
- `check_traces.py` (new): E1 and E2, with the negative control.
- `run_cex_suite.py` (new): E3. It deletes the `/tmp` harnesses first.
- `verify_all.sh`: new rows `traces` and `cex`; the mutated files include
  the model files; the mutation row counts the independent mutants by
  step.
- `coverage_bitwuzla.sh`: also counts the model file, and runs both new
  scripts (`NO_RUN=1` for the traces: the coverage tree's instrumented
  runtime library does not link into a native harness).
- `mutate_bitwuzla.py`: 25 mutants of the model code (`model:`), written
  by a separate agent.

## Mutation testing (U1)

[OBS 2026-11-10] A separate agent, which saw the code and the spec but no
test, wrote 25 mutants. It also found from Bitwuzla's source why some
would be hard to see: `assert_formula` and `check_sat` clear Bitwuzla's
last result, so `get_value` already refuses after them. A failed `add()`

[OBS 2026-11-10] First run: 18 of 25 caught. The 7 survivors:
- 4 about a model kept across a failed `add()` (no bump in `add`; bump only
  on success; every check counted as `sat`; `get_model` that logs but keeps
  the generation). No test had that sequence; with these bugs it returns
  the old model's value. New test case "model after an assertion it cannot
  encode".
- 2 about printing an old model (falls through; uses the solver's current
  generation). My test printed old models only while the solver had no
  assertions, so they printed nothing either way. The print test now prints
  an old model while the solver has assertions and a newer `sat` model.
- "reset does not bump generation": equivalent. After `reset` the
  Bitwuzla instance is new and refuses `get_value` until a check, and the
  next `add` or check bumps the generation anyway; `reset` also empties the
  printed assertions. Only the log differs. The bump stays, so the
  property does not depend on Bitwuzla's own check. Listed in
  `KNOWN_EQUIVALENT`.

Second run of the 7: 6 caught. So 24 of 25, and the survivor is
equivalent.

## Review (R1)

[OBS 2026-11-10] A fresh agent reviewed the code against the spec (a
frozen copy, since mutation was editing the tree). It found no defect in
the adapter: generation logic, lifetimes (`m_self` is the last member, so
destroyed first), exceptions, null results, callers, and the sign
convention all checked out. It found five weaknesses in the tests, each
confirmed in the code before acting:
1. The guard was tested only where Bitwuzla refuses anyway (the failed
   `add()` case was missing). Already fixed by the mutation round.
2. `check_traces.py` counted failures before adding the "no nondet values"
   problem, so that row could print FAIL and exit 0. Fixed.
3. E1 was checked on the harness modulo 2^32, so a signed numeral in the
   trace would pass. Now the trace's printed value must be exactly
   `0xffffffff:bv(32)` (or `4294967295:bv(32)`), and any `-` in a value of
   an `smt-bw` trace fails the row. Checked that this fires on Z3's
   `-1:bv(32)`. The reviewer also asked about `branch.c`'s blocks: the
   criteria (written before the code) require them for `inc.c` only, with
   the reason; the script now prints the others for information (all
   three equal in this run).
4. "Evaluating does not change the solver" could not fail (`x + 1 = 0` and
   `x = 0` is unsat anyway). Now: after evaluating `y` and `r`, which are in
   no assertion, asserting `y = value + 5` and `r = not value` must be sat
   with the new values.
5. A `nondet` value in the fuzzer would have reached Z3's encoder, which
   exits. Now counted as a non-value first.

Not changed, recorded below: struct values, the plan's wording (null Expr,
`print`), null input, log noise, Path BMC keeping a model.

## Correctness case (step 1.5)

**Claims.**
1. A value that `smt-bw`'s model gives is the value of the term under one
   assignment that satisfies every assertion.
2. A model gives no value once the solver has changed, the solver is gone,
   or the last check was not `sat`; it gives `nondet`.
3. Anything else it cannot evaluate gives `nondet`; it never guesses, and no
   exception escapes.
4. Counterexamples from `smt-bw` are real: run natively, they reach the
   error.

**Evidence.**
- Claim 1:
  - the fuzzer: 8 seeds × 4000 formulas, 25,052 `sat` models. Z3 accepted
    every model, and 448,032 term values (every subterm, plus terms over
    constants in no assertion) equal Z3's under the same assignment.
    Widths 1-128;
  - unit tests of exact values (255 on 8 bits, 2^128-1, widths 1 and 65,
    Bool), and that evaluating leaves the solver unchanged.
- Claim 2: unit tests of each change (add, failed add, check, check with
  nothing new, reset, unsat, unknown, destroyed solver, before any check),
  including the case where Bitwuzla itself would still answer. 25
  independent mutants: 24 caught, 1 equivalent (explained above).
- Claim 3: unit tests with integers, arrays, `select`, structs; the solver
  keeps working after them. Review found no escape path.
- Claim 4: all four `sat` examples with both solvers (9/9 with `mem.c`
  pending), trace values equal the harness's, a changed harness does not
  reach the error, `inc.c`'s harness is byte for byte Z3's; `test/cex`
  1/5 with the other 4 `unknown`.
- No regression: every other `verify_all` row as on 1ab43e7b.

**What everything depends on.** `decode_bitwuzla_value` (10 lines,
`MarshalBitwuzla.cc`); the generation check in `eval_in_model` and
`print_model`; the `++m_generation` in `add`, `check`, `reset`; the
assignment of `m_sat_generation` on `sat` and its test in `get_model`; the
`weak_ptr` lock in the model. Beyond our code: Bitwuzla's `get_value` (its
answers are what the fuzzer checks with Z3) and SeaHorn's trace and
harness code (checked end to end only on the examples).

**Not checked.**
- Struct values (`MK_STRUCT`) give `nondet`, while Z3's model evaluates
  each field. No formula with structs can be encoded yet, so no model
  meets one; plan 2.1.
- Array and function values: 1.6 and 1.7. The branch of `eval_in_model`
  for a value of another sort cannot be reached until then. llvm-cov
  shows it as run 7 times: those are the 7 exceptions caught just below.
  Clang derives counts by subtraction and does not account for exceptions,
  so a line right after a call that threw can show as run. That holds for
  every coverage number so far.
- If a model had no value for a nondet call, SeaHorn's harness writer would
  put 0 there (`CexHarness.cc:64-66`, also with Z3). It cannot happen in
  this step: every `sat` formula has only Bool and bit-vector terms.
- Path BMC keeps a model across later checks (`PathBmc.cc:966,1360`); with
  this adapter it would get `nondet`. Plan 2.4.
- A model used after a change logs an error on every `eval`, which can
  flood the log. Only a caller's bug can cause it.
- `eval` of a null Expr crashes, as Z3's does; no caller passes null.
- The text of the error log is not tested (why the one mutant is
  equivalent).
- End to end: four examples and one `test/cex` test; the fuzzer does not go
  through SeaHorn's trace code.

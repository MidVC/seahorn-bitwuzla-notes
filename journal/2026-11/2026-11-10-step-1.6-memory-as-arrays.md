# Step 1.6: memory as arrays

Plan step 1.6, started 2026-11-10 on `bitwuzla-support` after `8b85c705`,
under the verification rules in `URA/CLAUDE.md`.

Goal: programs that read and write memory (the default memory model, no
lambdas) get answers from `smt-bw`, and a `sat` answer comes with memory
contents in the trace.

## What the code has to fit (read before writing it)

[FACT] SeaHorn's array operators (`ExprOpArray.hh:13-18,102-107`):
`select(a, i)`, `store(a, i, v)`, `const-array(domain, v)` whose first
argument is the index sort (not the array sort, as in SMT-LIB), and
`array-map`, `array-default`, `as-array`. The sort is `ARRAY(index, value)`
(`ExprOpSort.hh:88-92`). Z3's encoder maps the first three one to one
(`ExprToZ.def:131-138`).

[FACT] Z3's model gives an array value as `store(... const-array(...) ...)`
when Z3 returns one, or an `ftable` when Z3 returns `as-array`
(`Z3.hh:397-423`). The harness writer reads memory through `ExprMemMap`,
which understands `store` chains over a `const-array` (`ExprMemMap.cc:16-19,
146-160`; `CexHarness.cc:107-160`).

[OBS 2026-11-10] With `smt-z3`, `mem.c`'s trace shows each memory as such a
chain, for example
`%sm2 store(store(const-array(bv(64), 0xbf800008:bv(64)), 0x8048008:bv(64), 0:bv(64)), 0x8048000:bv(64), 0x200000000:bv(64))`.
Words are 8 bytes at aligned addresses, little-endian: the load of `g[1]`
at `0x8048004` reads the upper half of the word at `0x8048000`, 2.

[OBS 2026-11-10] Bitwuzla 0.9.1, probes `probe16{,b,c}.cpp` in the session
scratchpad:
- `get_value` of an array gives a chain of `ARRAY_STORE` terms over a
  `CONST_ARRAY`, whose indices, elements and default are values. It is
  ordered by index. [SUPERSEDED → "Corrections from the review", 1] An
  array in no assertion gets `const-array(0)`.
- Equality between two constant arrays (`const(k) = const(3)`) answers
  `unknown`, with the warning "Equality over constant arrays not fully
  supported yet" (`array_solver.cpp:236-241`). [SUPERSEDED →
  "Corrections from the review", 2: the condition is wider] Every other probe of
  stores, selects, constant arrays, `ite` over arrays, extensionality, and
  arrays with 1- and 2-bit indices whose every index is written, gave the
  right answer.
- **A wrong model value:** for an array equality that is not in the
  assertions, `get_value` can be wrong. With 2-bit indices, `store` of all
  four indices to 7 over `const(3)` equals `const(7)`, but `get_value` of
  the equality says `false`; the same for a model array that is 5 at both
  indices of a 1-bit sort, compared with `const(5)`. The source says so: "This
  is not entirely correct since we have to check whether all indices have
  been overwritten" (`array_solver.cpp:174-177`). Asserted equalities are
  solved correctly. [SUPERSEDED → "Corrections from the review", 3: wrong
  mechanism, and asserted equalities can get wrong model values too]

[FACT] The trace asks the model only for Bool literals and instruction
values. A literal that evaluates to neither `true` nor `false` is skipped
(`BmcImpl.hh:14-33`), so `nondet` there loses detail but cannot mislead.

[OBS 2026-11-10] The four `test/cex` tests that use memory all run with
`--horn-bv2-extra-widemem`, which puts memory in structs (plan 2.1).

## Design decided before the code

- **Sorts:** `ARRAY(i, v)` with bit-vector `i` and `v` becomes Bitwuzla's
  array sort. Any other array sort (Bool, integer, array or struct index or
  element) is rejected, so the check answers `unknown`. SeaHorn's memory is
  bit-vector to bit-vector.
- **Operators:** `select` → `ARRAY_SELECT`, `store` → `ARRAY_STORE`,
  `const-array(domain, v)` → `mk_const_array(array sort of domain and v's
  sort, v)`. `=`, `!=` and `ite` over arrays need nothing new. Still
  rejected: `array-default`, `array-map`, `as-array`, finite maps, structs.
- **Bitwuzla's own `unknown`** (equality over constant arrays) is passed on
  as `unknown`. Encoding a constant array as a lambda to avoid it waits for
  1.7.
- **Model values of arrays:** decode the `store` chain down to its
  `const-array`, every index, element and default a value, into SeaHorn's
  `store(... const-array(index sort, default) ...)` in the same order, so it
  means the same function. Anything else gives `nondet`.
- **Model guard:** any term that contains an equality or disequality
  between arrays gives `nondet`, because of the wrong value above. This is
  simpler than computing such equalities ourselves, and the trace skips
  such literals.
- **Formula check:** constants of array sort (bit-vector to bit-vector),
  so formulas with memory are checked against Z3's encoding too.
- **Fuzzer:** arrays with 1-, 2-, 3- and 32-bit indices (small ones so that
  every index can be written), built from constants, `const-array`,
  `store` and `ite`, used by `select` and by `=` and `!=` between arrays.
- **Differences from the plan text:** the model guard is new (the plan did
  not know about the wrong value); array sorts are limited to bit-vector to
  bit-vector.
- **Added during the step, after E3 failed** (the criteria are unchanged):
  the model evaluates a struct (`MK_STRUCT`) field by field, as Z3's model
  does (`Z3.hh:399-405`). The plan had this in 2.1. With
  `--horn-bv2-extra-widemem` the formulas now encode, so `smt-bw` answered
  `sat` on three `test/cex` tests, but pointers and memories are struct
  registers there. The model gave `nondet` for them, so the harness had
  empty memory and did not reach the error (journal section "E3" below).
- **Added after the review (finding F1; criteria unchanged):** a second
  model guard. While an assertion has an equality or disequality between
  arrays with indices narrower than 32 bits, every term gives `nondet`. A
  struct is still a struct, of `nondet` fields. Bitwuzla can move such an
  assertion into a constant's definition, where the term guard cannot see
  it. With 32 bits or more, a wrong value would need one array value with
  2^31 stores, that is 2^31 accesses in the formula. SeaHorn's memories
  have 32- or 64-bit indices, so they are not affected.

## Pass criteria (written before the code)

Encoder and solver, unit tests in `units_bitwuzla`:
- A1. Read over write: `select(store(a, i, v), i) != v` is `unsat`;
  `i != j` and `select(store(a, i, v), j) != select(a, j)` is `unsat`;
  `select(store(a, i, v), j) != select(a, j)` alone is `sat`. With 64-bit
  indices and 8-bit elements, and with 2-bit indices.
- A2. `select(const-array(idx, 5), i) = 5` is valid; with 2-bit indices,
  storing 7 at all four indices of `const-array(3)` gives an array equal to
  `const-array(7)` (`unsat` for `!=`).
- A3. Rejected, naming the culprit: an array sort with a Bool, integer, or
  array index or element; `array-default`, `array-map`, `as-array`. Each
  makes the solver answer `unknown`, and it answers correctly after
  `reset()`.
- A4. A formula on which Bitwuzla answers `unknown` (equality of two
  constant arrays) gives `unknown` from the adapter, never `sat` or
  `unsat`.

Differential testing against Z3, in the random-formula fuzzer:
- D1. For formulas with arrays: whenever both answer, the answers agree, 0
  disagreements. Bitwuzla's `unknown`s are counted. Each one must be on a
  formula with an equality between arrays and a `const-array`, and they are
  at most 10% of the formulas.
- D2. Z3 accepts every `sat` model, array constants included: 0 rejected.
- D3. Every subterm of every `sat` formula is evaluated through the model.
  Bool and bit-vector values equal Z3's under the same assignment, as in
  1.5. An array value is a `store` chain of numerals over a `const-array`
  of a numeral, and Z3 proves it equal to the term under the same
  assignment. A term with an array equality inside gives `nondet` (counted
  as refused, never a value). 0 mismatches, 0 non-values, and both counts
  printed.
- D4. Formula check: every fuzzed formula `SAME`.
- D5. The fuzzer still exercises both answers: at least a quarter of the
  formulas `sat` and a quarter `unsat`, and at least a quarter of all
  formulas contain an array.

Models, unit tests:
- M1. After `select(a, 1) = 5` and `select(a, 2) = 7` (8-bit index and
  element), `eval(a)` is a `store` chain over a `const-array` that Z3
  proves has 5 at 1 and 7 at 2, and `eval(select(a, 1))` is 5. The same with
  a 64-bit index.
- M2. `eval` of a term with an array equality inside gives `nondet`,
  including probe16c's case where Bitwuzla's value is wrong; the solver
  keeps working.
- M3. The 1.5 guards hold for array terms too: after a change, `nondet`.
- M4. `print` lists array constants with their values.

End to end:
- E1. `mem.c` → `sat` with both solvers (pending mark removed). A new
  example whose writes cannot collide → `unsat` with both.
- E2. `mem.c`'s counterexample, with both solvers (`check_traces.py`): the
  trace prints, its nondet values equal the harness's, and the harness
  reaches the error natively. In addition, every memory value in the
  `smt-bw` trace is a `store` chain of numerals over a `const-array`, and
  every `load` in the trace shows the value that the memory printed for its
  `shadow.mem.load` holds at the load's address (8-byte little-endian
  words). The same load check must pass on `smt-z3`'s trace, so the check
  itself is tested. The memory contents need not equal `smt-z3`'s: `i`,
  `j` and the initial memory are free, so two correct models can differ.
- E3. `test/cex` with `smt-bw`: every test whose formula `smt-bw` can
  encode passes; each of the others answers `unknown` with the operator
  named.
- E4. Progress number: opsem/opsem2 per test against `smt-z3`, 0
  different. The number of tests with the same answer goes up from 106,
  and every remaining `unknown` names its operator, or is Bitwuzla's own
  (constant-array equality).
- E5. Formula check on opsem/opsem2: 0 `DIFFERENT`, 0 `UNDECIDED`; the
  number of `SAME` formulas goes up from 2485.
- E6. No regression: examples, traces, selector, detection, clam, units;
  `verify_all` passes.

## What was built

[FACT] SeaHorn branch bitwuzla-support, one commit for the step (hash in
"verify_all on the committed code" below):
- Encoder (`MarshalBitwuzla.cc`):
  - `ARRAY(i, v)` with bit-vector `i` and `v` becomes an array sort; any
    other array sort is rejected;
  - `select`, `store` and `const-array` are encoded; for `const-array`,
    the index sort comes from its first argument, and the error for a
    non-bit-vector index names the `const-array`;
  - `array-default`, `array-map` and `as-array` are still rejected.
- Model:
  - `decode_bitwuzla_value` decodes an array value (a store chain over a
    constant array, all values) into SeaHorn's `store(... const-array ...)`,
    in the same order;
  - the term guard: `nondet` for a term with an array equality or
    disequality inside;
  - the assertion guard (added after the review, below): while an assertion
    has an array equality with indices narrower than 32 bits, every term
    gives `nondet`;
  - a struct (`MK_STRUCT`) is evaluated field by field.
- Formula check: constants of array sort are declared to Z3 with their index
  and element widths.
- Tests in `units_bitwuzla` (31 test cases): arrays, array operators it
  cannot encode, model of arrays, model refusing array equalities, model
  after an equality of narrow arrays, structs, printing, formula check with
  arrays, and the old tests updated. The fuzzer now has arrays:
  - constants, `const-array`, `store`, `ite`, `select`, `=` and `!=`;
  - indices of 1, 2, 3 and 32 bits;
  - definitions of constants (`p = ...`, `x = ...`), which Bitwuzla
    substitutes;
  - it shares more subterms (55% instead of 25%) and favours one narrow
    width per formula, so that a quarter of the formulas are `unsat` (D5).

Scripts (URA/scratch, not in git):

  `unsat`).
- `check_traces.py` checks memory:
  - every memory value in an `smt-bw` trace is a store chain of numerals;
  - every load shows what the printed memory holds at its address;
  - `mem.c` has at least one load and one memory with each solver;
  - two negative controls: a doctored trace with a changed load value, and

## E3: the struct registers of widemem

[OBS 2026-11-10] With the encoder done, `smt-bw` answered `sat` on all
four memory tests of `test/cex`, but three of them failed: the harness ran
and did not reach the error. They run with `--horn-bv2-extra-widemem`, where
pointers and memories are struct registers. The model gave `nondet` for
them, so the harness had an empty segment for `memhavoc`, and its memory
held whatever the stack held (`mem_multi.c`: `[0 x ptr]` where Z3's harness
has `[3 x i64] [4294967231, ...]`). The answers were right; the
counterexample was not usable. Evaluating structs field by field, as Z3
does, fixed all three: `test/cex` 5/5 with `smt-bw`.

[FACT] `CexHarnessImpl.hh:210` reads `hPtrE->arg(0)` of a pointer's value.
For a bare `nondet`, which has no arguments, that reads out of bounds (with
Z3 too). With the struct branch, a widemem pointer is a struct, so this
needs an encoding failure or an out-of-date model.

against the spec, with no results of mine. Each finding was checked before
acting:
- **F1, a wrong model value (fixed).** The term guard looks at the term it
  is asked for. Bitwuzla first rewrites the assertions: an assertion
  `q = (a = b)` makes `q` a name for `(a = b)` (variable substitution,

  `q = (all7 = c7)` gives `q = false` (it must be true). With 1-bit

  Bitwuzla says the whole formula is true. Answers are unaffected.

  Fix: the assertion guard above. The new test case uses these probes, and
  checks that 64-bit indices still give the right values (`q` forced true
  gives `true`). The fuzzer now generates definitions; for a formula with
  a narrow array equality, every term must give `nondet`.
- **F2 (fixed):** no test had F1's shape. It is the new test case.
- **F3, F4:** the facts above got Bitwuzla's mechanism and two details

- **F5 (fixed):** `check_traces.py` did not require any memory to be

- **F6 (fixed):** the error for `const-array(int, v)` named the `int`

- **F7 (recorded):** caller hazards in SeaHorn's harness writer, which Z3

### Corrections from the review

1. [FACT] Store chains are ordered by Bitwuzla's node order, not by index
   (`std::map<Node, Node>` in `construct_model_value`; the reviewer's probe
   p3 has index 200 inside index 3). Nothing depends on the order: the
   indices are distinct.
2. [FACT] Bitwuzla answers `unknown` ("Equality over constant arrays not
   fully supported yet") in more cases than an equality of two constant
   arrays. It does so when an equality between arrays is true in its
   candidate model, and one side reaches a constant array while the other
   reaches an array constant, or two constant arrays of different values
   (`check_equality`, `array_solver.cpp:372-437`). The fuzzer's condition
   (an array equality and a `const-array` in the formula) covers this.
3. [FACT] The wrong value is not the `TODO` in `ArraySolver::value`. In
   0.9.1, `SolverEngine` asks the array solver only for selects, array
   constants and stores. An equality that is not registered after
   preprocessing goes to the evaluator, which compares the two values'
   terms (`evaluator.cpp:28`). The values are canonical
   (`construct_model_value`, `array_solver.cpp:804-903`: one store per
   index that an access touches, none equal to the default). So the
   comparison is wrong only for two different defaults whose stores
   together write every index: then one value has at least 2^(w-1)
   stores, one per access. Asserted equalities can be hit too, through
   substitution (F1).

   *Why I was misled:* I read the `TODO` next to the code that looked
   responsible, and my probe asked about an equality outside the
   assertions only, so it agreed with that reading.

## Correctness case (step 1.6)

**Claims.**
1. Formulas with memory as arrays (bit-vector to bit-vector) get the right
   `sat`/`unsat` from `smt-bw`. Anything it cannot encode, or that Bitwuzla
   does not fully support, gives `unknown`.
2. Bitwuzla gets exactly SeaHorn's formula: the encoding of array terms
   equals Z3's.
3. A model value of a Bool, bit-vector or array term is its value under one
   assignment that satisfies the assertions. Where Bitwuzla 0.9.1 can get a
   value wrong (array equalities), the model gives `nondet`.
4. Counterexamples with memory are real: run natively, they reach the
   error, and the trace's memory agrees with its loads.

**Evidence.**
- Claim 1:
  - 8 x 4000 random formulas, 58% with arrays, give 0 disagreements with
    Z3;
  - the 1,101 `unknown`s all have an array equality and a `const-array`;
  - unit tests: read over write, extensionality, `ite` over arrays,
    constant arrays, full overwrite of 2-bit arrays;
  - opsem/opsem2: 170 the same as `smt-z3` (was 106), 0 different, and the
    5 `unknown`s named;
  - 45 independent mutants: 44 caught, 1 equivalent.
- Claim 2: every fuzzed formula (32,000) and every formula of opsem/opsem2
  that Bitwuzla got (2953, was 2485) proved equal to Z3's encoding. Unit
  tests show the check finds wrong array encodings.
- Claim 3:
  - 267,792 model values equal Z3's under the same assignment, 30,400 of
    them arrays, proved equal as functions;
  - every term with an array equality, and every term of a formula with a
    narrow one, came back `nondet` (118,275, 0 not);
  - unit tests rebuild the reviewer's three wrong-value probes and get
    `nondet`, and 64-bit indices still get right values;
  - the 31/32-bit boundary is tested.
- Claim 4:
  - `mem.c`'s counterexample reaches the error natively with both solvers;
  - its one load reads what the printed memory holds;
  - three doctored traces fail the memory checks;
  - `test/cex` gives 5/5 with `smt-bw` (was 1/5), including the three
    widemem tests that need struct values.

**What everything depends on.**
- The array cases of `kindOf`, `termArgs` and `mkNode` (`CONST_ARRAY`),
  and `encode_sort`'s array branch.
- `decodeArray`.
- The two guards in `BitwuzlaSolverImpl.cc`: `hasArrayEquality`, its use in
  `eval_in_model`, and `m_narrow_array_eq`, set in `add()` and cleared in
  `reset()`.
- The `MK_STRUCT` branch of `eval_in_model`.
- Beyond our code:
  - Bitwuzla's array solver, whose answers the fuzzer checks against Z3;
  - the argument that a wrong array-equality value needs every index
    written (from Bitwuzla's source: `evaluator.cpp:28`,
    `construct_model_value`; traced by two reviewers);
  - SeaHorn's trace and harness code, checked end to end on `mem.c` and
    `test/cex` only.

**Not checked.**

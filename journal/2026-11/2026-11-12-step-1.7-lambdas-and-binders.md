# Step 1.7: lambdas and binders

Plan step 1.7, started 2026-11-12 on `bitwuzla-support` after `29b09883`
(1.6, not yet pushed), under the verification rules in `URA/CLAUDE.md`.

Goal: `--horn-bv2-lambdas`, SeaHorn's lambda memory model, gets answers from
`smt-bw`.

## What the code has to fit (read before writing it)

[FACT] In lambda mode, memory registers are arrays (`MemSortTy` is
`ARRAY(ptr, word)`, `BvOpSem2RawMemMgr.cc:161`). When one is read, it is
first wrapped as `lambda addr. select(A, addr)` (`coerceArrayToLambda`,
`BvOpSem2MemRepr.cc:699-707`). From there on:
- a store is `lambda addr. ite(addr = p, v, fapp(mem, addr))`
  (`BvOpSem2MemRepr.cc:469-477`);
- memset and memcpy are lambdas with range conditions (`:113-179,
  512-600`);
- a load is `fapp(mem, addr)`.

The bodies use `bvar(0)` for the bound address.

[FACT] SeaHorn's de Bruijn indices follow Z3's, as far as opsem uses them:
index 0 is the last variable of the innermost binder. They differ from Z3
for nested binders of more than one variable, which opsem never builds
(journal 2026-10-22, encoder). The default PHI encoding asserts
`edge => (phi = val)`, so a memory PHI asserts "array = lambda"
(`VCGen.cc:287-305`).

[FACT] Z3's encoder treats a `fapp` of a term as `select`, because lambdas
are arrays in Z3 (`ExprToZ.def`, `mk_bind_core`). Z3's model gives a
lambda-mode memory as `store(... const-array ...)`. The `smt-z3` trace of
`mem.c` with `--horn-bv2-lambdas` shows `%sm2 store(const-array(bv(64),
0:bv(64)), 0x8048000:bv(64), 0x200000000:bv(64))` (seen 2026-11-12).

[OBS 2026-10-22] (first attempt) Bitwuzla 0.9.1:
- a lambda has a function sort, not an array sort;
- `EQUAL(array, lambda)` throws, and `ARRAY_SELECT(lambda, i)` and
  `APPLY(array, i)` both throw;
- equality between functions answers `unknown`;
- `ITE(c, lambda1, lambda2)` aborts the process in `check_sat`;
- nested lambdas are merged into one function of several arguments;
- an unbound variable is silently accepted.

[OBS 2026-11-12] Bitwuzla 0.9.1, probes `probe17.cpp`, `probe17b.cpp` in
the session scratchpad:
- `get_value` of a function constant is a lambda over an `ite` chain of
  values. `get_value` of a lambda over constants returns the lambda itself,
  constants and all, so it is not a value.
- `c => forall y. b[y] = lam(y)` with `b[p] != 7` gives `sat`, and `unsat`
  once `c` holds, as it should. With `q = forall ...` asserted, the model
  checked by hand satisfies it.
- [FACT] Values of quantifiers:
  - a `forall` registered in the assertions takes the value of its
    abstraction;
  - a `forall` that is not registered makes `get_value` register it and
    solve again (`solver_engine.cpp:236-264`, `:500-507`).

  So reading values can run the solver again, and values read before and
  after might come from different models. In probe17b they did not
  change.
- [OBS] Z3 parses Bitwuzla's printed lambdas, a lambda applied directly,
  and a `let`-bound lambda applied (`((lambda ...) a)`, `(_let0 p)`). It
  proves Bitwuzla's `c => forall y. b[y] = lam(y)` equal to SeaHorn's
  `c => b = lam` (`p1-p3.smt2`).

[FACT] `verify_all`'s answers row reruns only the first seahorn/sea
command of each test (`rerun_lit_tests.py`: `cmds[:1]`). So the
`--horn-bv2-lambdas` RUN lines, usually second, have never been compared
answer by answer.

## Design decided before the code

Encoder (much of it from the first attempt, `0efbdadc`):
- **Binders:** `lambda`, `forall`, `exists`.
  - Bound variables of bit-vector or Bool sort become fresh named
    Bitwuzla variables for each binder; other sorts are rejected.
  - `bvar(i)` follows Z3's convention; one outside its binder, or of
    another sort than its binder's, is rejected.
  - A term with a free bound variable is cached only under its binder;
    closed terms are cached for good.
  - A lambda whose body is a function is rejected, because Bitwuzla would
    merge them.
- **Application:**
  - `fapp` of a term (not a declaration) is `APPLY` on a function and
    `ARRAY_SELECT` on an array (one argument);
  - `select` on a function is `APPLY`;
  - `store` on a function is `lambda x. ite(x = i, v, f(x))`.
- **Equality** with a function on either side is stated pointwise:
  `forall xs. a(xs) = b(xs)`; `!=` is its negation.
- **ITE** with a function in a branch is moved inside a lambda:
  `lambda xs. ite(c, t(xs), e(xs))`.
- **Still rejected:** uninterpreted functions (declarations with
  arguments), and function-sorted constants.

Model:
- A function value gives `nondet`. Decoding lambdas into store chains, as
  Z3's model does, waits until a caller needs it (the plan allows this).
  Lambda-mode traces show `nondet` for memory that is a lambda; array
  registers still decode.
- **Quantifier guards**, because reading a value can solve again
  (above):
  - a term with `forall` or `exists` inside gives `nondet`;
  - while an assertion has one, every term gives `nondet`.

  The cost: no trace values for a lambda-mode program whose memory meets
  at a PHI, under the default PHI encoding; the answer is unaffected.

Formula check:
- Bound variables, lambdas and quantifiers inside the term are accepted;
  only free constants are declared to Z3.
- The check refuses (UNCHECKED) a term where a bound variable has a
  constant's name, so a printed name cannot mean two things.

Answers row: `rerun_lit_tests.py` reruns every RUN line, keyed
`test#k`. `compare_answers.py` reports both the RUN lines and the first
lines only, the latter comparable with earlier steps.

Added during the step (the criteria are unchanged):
- **Formula check printing.** [OBS 2026-11-12] Bitwuzla 0.9.1 prints a term
  with binders wrongly when a subterm is shared inside and outside a binder:
  let names leave their scope (probe17d), and `print_formula` does the same
  (probe17e). For such a term the check now gives every closed subterm a
  let of its own at the top, children first, with a fresh name `_bwcN`.
  Each is printed by Bitwuzla without lets, over the names of its closed
  subterms. (`define-fun` instead of `let` made Z3 5.1.0 answer wrongly: a
  "difference" on formulas that are equal.)
- **Pointwise equality, printed for Z3.** `(forall xs (= (a xs) (b xs)))`
  with closed `a` and `b` is printed as `(= a b)`. That is the same
  formula (extensionality), and Z3 decides it for arrays and lambdas where
  it gave up on the quantifier. A wrong pointwise encoding would still
  print as what it means, so this cannot hide one.
- **A difference must be confirmed.** Z3's `sat` is reported `DIFFERENT`
  only if, under its values, the two sides evaluate to different values.
  Otherwise it is `UNDECIDED`. For a formula with a quantifier, Z3's `sat`
  is always `UNDECIDED`. [OBS] Z3 5.1.0 answered `sat`, and even evaluated
  its values wrongly, on equal formulas with equalities between lambdas.
  `SAME` still needs Z3's proof.
- **A time limit per check:** `bitwuzla_solver_impl(time_limit_ms)`,
  Bitwuzla's `TIME_LIMIT_PER`; a check that runs out answers `unknown`.
  [OBS] A fuzzed formula with a 32-bit function equality kept Bitwuzla's
  quantifier procedure busy for over 10 minutes. The default is no limit,
  as before. A SeaHorn option for it is plan 2.2.
  [OBS 2026-11-13] **The limit does not bound quantifiers.** A check in the
  expansion test ran 3 hours in `QuantSolver::substitute`, past a 5 s
  limit. [FACT] Bitwuzla 0.9.1 looks at the limit (`d_env.terminate()`)
  in `BvSolver::solve` (`bv_solver.cpp:104`), not in `quant_solver.cpp`
  or the solving loop. So in lambda mode a hard quantified formula can
  hang SeaHorn, limit or not. The fuzz tests therefore first run a
  quantified check in a child process, killed after 4 times the limit
  (`boundedCheck`); if the child finishes, the same deterministic check
  runs in the test. Plan 2.2 needs a process-level limit for this.
- **Answers row:** `compare_answers.py` labels `Z3-UNKNOWN` when `smt-z3`
  answers `unknown` and `smt-bw` answers; that is not a disagreement.

Fuzzer, added to the random formulas:
- lambdas `lambda x. ite(x = i, v, f(x))` over `lambda x. A[x]` and
  constant lambdas;
- their application, `select` and `store` on them;
- `ite` over lambdas;
- equalities and disequalities between functions, and between a function
  and an array;
- `forall` and `exists` over small bit-vectors.

## Pass criteria (written before the code)

Encoder and solver, unit tests in `units_bitwuzla`:
- L1. Application: `(lambda x. x + 1)(3) = 4` is valid; a memory read
  `(lambda x. ite(x = p, v, A[x]))(p) = v` is valid; `select` and `store`
  on a lambda behave like on an array.
- L2. Scoping:
  - the same `bvar(0)` Expr under two different lambdas means each one's
    own variable;
  - `bvar(1)` under a nested binder refers to the outer one;
  - a bound variable outside its binder, or of the wrong sort, is
    rejected;
  - the encoder still works after a rejection inside a binder.
- L3. Equality: `A = lambda`, `lambda = lambda` and `!=` give the right
  `sat`/`unsat`, also under an implication; `ite` over lambdas gives the
  right answer and does not crash.
- L4. Quantifiers: small `forall` and `exists` formulas over bit-vectors
  give the right answer; any `unknown` is counted, not taken as an answer.
- L5. Rejected, naming the culprit: a lambda whose body is a function; an
  uninterpreted function; a bound variable of array sort. Each makes the
  solver answer `unknown`, and it answers correctly after `reset()`.

Models, unit tests:
- M1. A function value gives `nondet`; the value of an application of a
  lambda is right (equal to Z3's).
- M2. A term with a quantifier gives `nondet`; while an assertion has a
  quantifier, every term gives `nondet`; after `reset()`, values come back.

Formula check, unit tests:
- F1. Formulas with lambdas, application, pointwise equality and
  quantifiers come out `SAME`; a wrong encoding of each comes out
  `DIFFERENT`; a bound variable named like a constant is `UNCHECKED`.

Differential testing against Z3, in the fuzzer:
- D1. With lambdas and quantifiers in the formulas: 0 disagreements where
  both answer. Bitwuzla's `unknown`s are counted. Each one must be on a
  formula with a quantifier (from a function equality or `forall`/
  `exists`) or the 1.6 condition (an array equality and a `const-array`),
  and they are at most 10% of the formulas.
- D2. Every `sat` model with values is accepted by Z3; a model of a formula
  with a quantifier must have no values (counted).
- D3. Every term evaluated through a model with values equals Z3's value.
  Applications of lambdas are among the terms. Terms the guards refuse
  give `nondet`. 0 mismatches, 0 non-values, 0 not refused.
- D4. Every fuzzed formula `SAME` in the formula check.
- D5. At least a quarter of the formulas `sat` and a quarter `unsat`, a
  quarter with a lambda, and a tenth with a quantifier.

End to end:
- E1. New examples with `// Flags: --horn-bv2-lambdas`:
  - `mem` → `sat` and `mem_safe` → `unsat`;
  - one where memory meets at a PHI, so the pointwise equality reaches the
    solver, with each answer.

  Both solvers agree with the expected answers.
- E2. The `sat` lambda examples' counterexamples (`check_traces.py`): the
  trace prints, its nondet values equal the harness's, and the harness
  reaches the error natively. Memory values may be `nondet` (the model
  design above). The 1.6 memory checks still pass on the default-mode
  examples.
- E3. opsem/opsem2, every RUN line against `smt-z3`: 0 different. The lit
  pass count with `smt-bw` rises from opsem 87 and opsem2 47. Every
  remaining `unknown` names its operator, or is Bitwuzla's own (quantifier
  or constant-array equality).
- E4. Formula check on opsem/opsem2: 0 `DIFFERENT`, 0 `UNDECIDED`, 0
  `UNCHECKED`; `SAME` rises from 2953.
- E5. No regression: `verify_all` passes; `test/cex` 5/5 with both.

Rules from `URA/CLAUDE.md`:
- U1. Mutation: a separate agent that has not seen the tests writes bugs
  for the new code. Each is caught or explained.
- C1. Coverage: every new line is run by a test, or listed with a reason.
- R1. A fresh review of the code against the spec; each finding checked
  before acting on it.
- S1. Unsupported binders, sorts and shapes answer `unknown`. Bitwuzla's
  own `unknown` (quantifiers, function equality) is passed on. The model
  gives `nondet` for function values and under the quantifier guards. The
  correctness case says how.

## What was built

"verify_all on the committed code" below):

  - binders with scopes;

### Fuzzer design changed during the step (criteria unchanged)

[OBS 2026-11-12] The design said the fuzzer would have equalities with
functions and stores into functions. Both were taken out:
- **A random equality between a 32-bit function and an array** kept
  Bitwuzla's quantifier procedure busy for over 10 minutes (formula 106).
  With time limits, Z3 was undecided ("incomplete (theory array/lambda)")
  or wrong (formulas 207, 528) on several. The formula check could not judge
  them, and a run took over 25 minutes.
- **A store into a function compared with an array** made Z3 incomplete on
  its own encoding (formula 490).

What covers them instead:
- unit tests (L3, and the check tests);
- SeaHorn's lambda-mode formulas in the formula check: every memory PHI
  there is a pointwise equality, all `SAME`;
- the `memphi` examples;
- after the review, "function equalities against an expansion":
  - random formulas with an equality between a function and a function or
    an array, over 1- to 3-bit indices, and with stores into functions;
  - Bitwuzla gets the formula; Z3 gets it with each such equality expanded
    into one equality per index, which it decides;
  - 300 formulas by default: 289 agree (205 `sat`, 84 `unsat`), 0
    disagree, 11 unknown to Bitwuzla.

To keep a quarter of the formulas `unsat` (D5), subterms are shared a
little more (60%).

[OBS 2026-11-12] One example design: a join where both branches store
(`if (c) g[j] = 2; else g[(j+1)%4] = 3;`) made `smt-z3` answer `unknown`;
`smt-bw` answered `sat`. The example now stores on one branch only, which
Z3 decides.

## Correctness case (step 1.7)

**Claims.**
1. Formulas with lambdas, applications, stores into functions, function
   equalities and quantifiers get the right `sat`/`unsat` from `smt-bw`.
   Shapes it cannot encode (a lambda whose body is a function, an
   uninterpreted function, a bound variable of another sort) give
   `unknown`.
2. Bitwuzla gets exactly SeaHorn's formula: each bound variable refers to
   its own binder.
3. A model value is right or `nondet`. Values of applications equal Z3's.
   A function, a term with a quantifier, and every term while an assertion
   has a quantifier get `nondet`.
4. Counterexamples of lambda-mode programs whose memory meets at no PHI
   are real.

**Evidence.**
- Claim 1:
  - 32,000 random formulas (30.5% with lambdas, 45.3% with quantifiers): 0
    disagreements with Z3, and the 948 `unknown`s all explained;
  - 16,000 formulas with function equalities and stores into functions,
    against Z3 on the expansion: 0 disagreements;
  - opsem/opsem2, every RUN line: 289 of 293 the same as `smt-z3`, 0 different; the 2 `unknown`s are default-mode lines (constant-array equality);
  - lit with `smt-bw`: opsem 123 + 1 expected failure (was 87 + 1),
    opsem2 50/50 (was 47);
  - unit tests L1 to L5 (38 test cases in all);
  - 41 mutants by a separate agent: 36 caught, 5 equivalent (explained
    above).
- Claim 2:
  - 32,000 fuzzed formulas `SAME` in the formula check;
  - 3089 opsem/opsem2 formulas `SAME` (was 2953), and 38 more from the 3 RUN lines lit skips, checked by hand, every lambda-mode memory PHI among them;
  - unit tests: wrong encodings are `DIFFERENT` (quantifier-free) or never
    `SAME` (quantified); the pointwise printing has negative tests; free
    variables and repeated names are `UNCHECKED`.
- Claim 3:
  - 137,377 model values equal Z3's (15,304 arrays);
  - 154,149 terms refused, 0 not refused; 12,178 models with no values;
    3,842 functions `nondet`;
  - unit tests M1, M2 (values come back after `reset()`).
- Claim 4: `mem_lambda.c`'s counterexample reaches the error natively with
  both solvers; `test/cex` 5/5 with both (default mode).

**What everything depends on.**
- Encoder (`MarshalBitwuzla.cc`):
  - `enterBinder`/`leaveBinder` and `mkBoundVar` (a de Bruijn index to its
    scope);
  - `lookup`/`remember` (a term with a free bound variable is cached only
    in its innermost scope);
  - `freshVar`'s distinct names;
  - `mkApp`, `mkEq` (pointwise), `mkIte` (an `ite` of functions moved
    inside a lambda), `mkStore` on functions;
  - the `catch (...)` that clears the scopes after a rejection.
- Solver (`BitwuzlaSolverImpl.cc`): `hasQuantifier`, `m_quantified` (set
  in `add()`, cleared in `reset()`), and the term guard in
  `eval_in_model`.
- Formula check: `printWithLets`, the pointwise printing, the confirmation
  of a `DIFFERENT`, and `UNDECIDED` for Z3's `sat` on a quantified formula.
- Beyond our code:
  - Bitwuzla's quantifier procedure, checked against Z3 where Z3 decides
    (and on expansions where Z3 does not);
  - SeaHorn's de Bruijn convention, the same as Z3's for the binders opsem
    builds;
  - Z3 as the reference, which is incomplete on lambda equalities and was
    once wrong there. Hence the expansion test.

**Not checked.**
- **Time.** Bitwuzla's time limit does not stop its quantifier procedure,
  and a `Terminator` would not either. Both go through
  `Env::terminate()` (`env.cpp:84-88`, `resource_terminator.cpp:10-16`),
  which preprocessing, `BvSolver::solve` (`bv_solver.cpp:104`) and the SAT
  solvers check, and nothing in `src/solver/quant/` does. A lambda-mode
  program with a hard memory-PHI `forall` can hang `smt-bw`; not seen in
  opsem/opsem2. SeaHorn has no time limit for `smt-bw` yet (plan 2.2),
  and 2.2 needs a process-level limit for this.
- Models of lambda-mode programs whose memory meets at a PHI: no values
  (E2 above). Function values are `nondet` (parked: decode lambda values).
- Nested binders of more than one variable, where SeaHorn's convention
  differs from Z3's: opsem never builds them. The encoder follows Z3's, and
  the tests build them only that way.
- Equalities with 32-bit functions: random formulas leave them out (Z3
  cannot judge them); they are covered by unit tests and SeaHorn's own
  formulas. The expansion test uses 1- to 3-bit indices.
- Two equivalent mutants rely on Bitwuzla 0.9.1 storing `forall a b` as
  `forall a. forall b`.
- `printWithLets` is quadratic (parked); only the check option is slowed.
- `verify_all`'s formulas row covers only the RUN lines lit runs. The 3 it skips with `smt-bw` were checked by hand (38 `SAME`), not by `verify_all`.
